Azkashine Job Portal — Procurement & Integration Guide

External services to onboard: Google OAuth · Razorpay · DLT · MSG91 (SMS · WhatsApp · Email)
Audience: Procurement / Operations · Output goes to the BE team for wiring
Status: Run-sheet for Sprint 1 external dependencies

Overview & Priority Order

Read this first — it tells you what to start in parallel today vs. what waits.

The job portal depends on four external services being onboarded before the backend can finish wiring real authentication, real payments, and real notifications. Each has a different approval clock — some are 5-minute signups, others are 1–3 week regulatory reviews.

Why this guide exists

The BE team can code against all of these in minutes, but real-world traffic (real OTPs, real money, real WhatsApp messages) needs procurement-side approvals first. This guide tells the procurement / operations owner exactly what to click, what documents to upload, and what credentials to hand back to the BE team.

The four services & what blocks what

Razorpay Payments — ₹50 lifetime (seeker) + ₹250/mo (employer) Test: instant · Live: 3–4 days S1-17 (Subscription module + webhooks)

1. Register Google OAuth Client S1-04

Time: 30 min clickwork · Approval: none · Output: Client ID + Secret to BE team

All clickwork in Google Cloud Console — no code. Enables "Sign in with Google" on the website, mobile app, and admin panel.

1.1 Create the GCP project

Why: Google's OAuth credentials always live inside a Cloud project. Creating it under the Azkashine Workspace org keeps ownership with the company instead of a personal Gmail.
  1. Go to https://console.cloud.google.com/
  2. Sign in with an Azkashine Google Workspace account (not personal Gmail — ownership stays with the org).
  3. Top bar → project dropdown → New Project
    • Name: Azkashine Job Portal
    • Organization: azkashine.com (must show up if you're signed in with workspace)
    • Location: same org
  4. Create → wait ~30s → switch into the new project.

1.2 Enable the required API

Why: OAuth login needs to fetch the user's email and name from Google. The People API is what exposes that.
  1. Left nav → APIs & Services → Library
  2. Search People API → click Enable.

You don't need Gmail API, Drive API, etc. — those are for accessing user data we never touch.

1.3 Configure OAuth consent screen

Why: This is the "Azkashine wants to access your Google account" screen users see during login. Google needs us to declare what we're asking for before they let us ask.
  1. Left nav → APIs & Services → OAuth consent screen
  2. User Type:
    • Internal for now (only @azkashine.com users can sign in — perfect for dev).
    • Switch to External before prod launch (lets any Google account sign in; requires Google verification if you exceed 100 users).
  3. App information:
    • App name: Azkashine Job Portal
    • User support email: support@azkashine.com (or whoever owns support)
    • App logo: optional for internal, required for external verification
  4. App domain (external only):
    • Application home page: https://azkashine.com (or staging URL)
    • Privacy policy URL + Terms of service URL — required for external; skip for internal
  5. Developer contact: your email
  6. Scopes → Add:
    • openid
    • .../auth/userinfo.email
    • .../auth/userinfo.profile

    Don't add anything else — extra scopes trigger Google's sensitive/restricted scope review and slow you down weeks.

  7. Test users (external + testing mode): add team Gmail addresses so they can log in before verification.
  8. Save.

1.4 Create the OAuth 2.0 Client IDs

Why: Each platform (web / iOS / Android) needs its own Client ID so Google knows where login requests are coming from and where to redirect after the user signs in.

Left nav → APIs & Services → Credentials → + Create Credentials → OAuth client ID

1.4a Web client Do this first

Unblocks the BE team immediately.

  • Application type: Web application
  • Name: Azkashine Web
  • Authorized JavaScript origins:
    • http://localhost:3000
    • http://localhost:5000 (BE dev port)
    • https://staging.azkashine.com (confirm with senior)
    • https://azkashine.com (prod — can add later)
  • Authorized redirect URIs:
    • http://localhost:5000/api/auth/google/callback
    • https://staging.azkashine.com/api/auth/google/callback

    Confirm exact path with the BE team before saving; safe default is /api/auth/google/callback.

  • Create → you'll get Client ID + Client Secret. Download the JSON too.

1.4b Android client Blocked on S1-05

Why blocked: Need the mobile workspace to be set up first so the mobile dev can give you the package name + SHA-1 fingerprint.

When mobile dev has the workspace ready, you'll need from them:

  • Package name (e.g. com.azkashine.jobportal)
  • SHA-1 fingerprint — they run: keytool -list -v -keystore <path> -alias <alias>
  • Need both debug SHA-1 (dev builds) and release SHA-1 (Play Store builds).

Then: Create Credentials → OAuth client ID → Android → paste package name + SHA-1. No secret for Android.

1.4c iOS client Blocked on S1-05

From mobile dev: Bundle ID (e.g. com.azkashine.jobportal).

Create Credentials → OAuth client ID → iOS → paste bundle ID. No secret for iOS.

1.4d Admin client

Per the ticket: share the web client — the admin panel is a web app too. Just add its origin (e.g. http://localhost:3001 or https://admin.azkashine.com) to the existing Web client's authorized origins/redirects. Don't make a separate one unless senior insists.

1.5 Store secrets in the vault

Why: Client Secrets are like passwords for the app. If they leak on GitHub or chat, anyone can impersonate Azkashine to Google. They live ONLY in a secrets vault.

Confirm with senior which vault is used (1Password / Bitwarden / Vaultwarden / Doppler?). For each client, store:

Service: Google OAuth — Azkashine Job Portal
Environment: dev / staging / prod
Client ID: <id>.apps.googleusercontent.com
Client Secret: <secret>            ← web only; mobile clients have no secret
Authorized origins: <list>
Authorized redirect URIs: <list>
GCP Project: azkashine-job-portal
Owner: ops@azkashine.com

Do NOT commit to git. BE team will read these from .env (local) and from whatever secret manager staging/prod uses.

1.6 Hand off to the BE team

Why: BE team can't wire login until they have these three values. Send them in a DM, not a public channel.

DM/email with:

  • GOOGLE_CLIENT_ID=...
  • GOOGLE_CLIENT_SECRET=...
  • Redirect URI you registered (so they wire the exact same path)
  • Vault link for future rotation

Ask them to confirm received → tick the last acceptance criterion on the ticket.

Gotchas

  • Workspace account matters — if you create the project under a personal Gmail, you can't set User Type = Internal, and you'll lose Azkashine ownership when you leave. Use @azkashine.com.
  • Redirect URI must match exactly — http vs https, trailing slash, port number all matter. Mismatch = redirect_uri_mismatch error in BE.
  • Internal app + external user trying to log in = "Access blocked" — switch to External + add test users, or wait until prod-ready and submit for verification.
  • SHA-1 for Android — debug builds and release builds have different SHA-1s. Add both to the Android client.
  • Don't enable too many scopes — only openid email profile. Anything else triggers Google's restricted-scope verification — weeks of back-and-forth.

2. Register Razorpay (Payment Gateway)

Time: 30 min clickwork · Test mode: instant · Live mode: 3–4 working days (KYC) · Output: API keys + Plan ID + Webhook secret

BE team can integrate against test mode in ~10 minutes; live mode for real money takes 3–4 working days of KYC review.

2.1 Create the Razorpay account

Why: Razorpay is the gateway between our checkout and the user's bank. Without an account, no money can flow. Signing up with the company domain keeps ownership with Azkashine, not an individual.
  1. Go to https://dashboard.razorpay.com/signup
  2. Sign up with an @azkashine.com email (not personal Gmail).
  3. Enter:
    • Business name: Azkashine (must match PAN / GST exactly)
    • Mobile number (receives OTP)
    • Password
  4. Verify mobile OTP.
  5. Dashboard loads. Top-right environment toggle defaults to Test Mode — keep it there for now.

2.2 Generate Test Mode API Keys

Why: Test mode lets the BE team wire and test the whole payment flow with fake card numbers, while live KYC is still being reviewed. No KYC needed for test keys.
  1. Left nav → Account & Settings → Website and app settings → API Keys
    Direct link: https://dashboard.razorpay.com/app/website-app-settings/api-keys
  2. Confirm top-right says Test Mode.
  3. Click Generate Test Key.
  4. You get:
    • Key ID — starts with rzp_test_... (safe to share, even lives on frontend)
    • Key Secret — shown ONCE only. Click "Download Key Details" to save a JSON, or copy immediately.
  5. Save both in the vault.
If you lose the secret → click Regenerate Test Key. The old one stops working immediately.

2.3 Set up the Razorpay Webhook

Why: When a customer pays, Razorpay needs to TELL our backend "payment succeeded — upgrade them to Pro." Without a webhook, BE has no reliable way to know. Webhooks also handle monthly auto-debits firing on their own.
  1. Left nav → Account & Settings → Webhooks
    Direct link: https://dashboard.razorpay.com/app/webhooks
  2. Click + Add New Webhook.
  3. Fill in:
    • Webhook URL: https://staging.azkashine.com/api/webhooks/razorpay (for staging) — for local dev BE team uses ngrok to expose localhost:5000; they'll give you the URL
    • Secret: type any strong random string (e.g. azk_rzp_whk_a7Xq92Lm) — Razorpay signs every webhook with this so BE can verify it's actually from Razorpay
    • Active Events → tick:
      • payment.captured — one-time payment ₹50 succeeded
      • payment.failed
      • subscription.activated — employer signed up for ₹250/month
      • subscription.charged — monthly auto-debit succeeded (fires every month)
      • subscription.halted — mandate failed too many times → downgrade
      • subscription.cancelled
      • subscription.pending
      • refund.created
  4. Click Create Webhook.
  5. Save the webhook secret as RAZORPAY_WEBHOOK_SECRET in the vault.

Add a SECOND webhook for production later (same setup, different URL like https://api.azkashine.com/api/webhooks/razorpay).

2.4 Create Subscription Plans (for employer ₹250/month)

Why: Recurring plans need a Plan object on Razorpay's side — that's the template every employer subscribes to. Once made, every new subscriber automatically uses the same billing rules.
  1. Left nav → Subscriptions → Plans
    Direct link: https://dashboard.razorpay.com/app/subscriptions/plans
  2. Click + Create Plan.
  3. Fill in:
    • Plan Name: Azkashine Pro Monthly
    • Billing Frequency: Monthly
    • Billing Cycle: 1 month
    • Amount: ₹250 (Razorpay stores it as 25000 paise internally)
    • Currency: INR
    • GST: enable "Add GST" — Razorpay calculates 18% on top automatically (employer pays ₹250 + 18% = ₹295 total).
  4. Click Create Plan.
  5. Save the Plan ID (e.g. plan_NXyZ123abc) — BE team puts it in .env as RAZORPAY_PLAN_PRO_MONTHLY.
Note on ₹999 vs ₹250: CLAUDE.md says ₹250, newer SUBSCRIPTION_S1_PLAN.md says ₹999. Confirm the actual locked price with senior before creating the plan — wrong amount means every subscription has to be migrated later.

For the ₹50 lifetime seeker plan: this is a one-time payment, NOT a recurring subscription. So you don't create a Plan for it — BE team will use Razorpay's Orders API per-purchase. No setup needed in the dashboard.

2.5 Submit KYC for Live Mode

Why: Test mode only accepts fake cards. For real money to actually flow from real users into a real bank account, Razorpay (regulated by RBI) must verify Azkashine is a real business. This is the KYC step.

Takes 3–4 working days. Until KYC is approved, you can only accept test cards (e.g. 4111 1111 1111 1111).

  2. Step 1 — Business Type: Pick the right entity (Proprietorship / Pvt Ltd / LLP / Partnership / Trust / NGO).
  3. Step 2 — Business Details:

    • Business category: Services → Employment Agencies & Temporary Help Services
    • MCC code: 7361 (filled automatically based on category)
    • Business description: e.g. "Online job portal connecting employers and job seekers in India"
    • Website URL: https://azkashine.com (must be live — Razorpay's bot crawls it)
  4. Step 3 — Documents to Upload:

  5. Step 4 — Bank Account (where settlements land):
    • Account holder name (must match PAN)
    • Account number + IFSC
    • Razorpay does a penny drop — sends ₹1 → verifies the name from the bank — usually instant.
  6. Step 5 — Website Compliance Check: Razorpay manually reviews the live site for these pages — must exist and be accessible before submitting:

2.6 Generate LIVE Mode API Keys (after KYC approved)

Why: Test keys never charge real cards — they're a separate sandbox. Once KYC clears, you have to generate a fresh set of LIVE keys to start accepting real money. Plans and webhooks don't carry over either.
  1. Top-right toggle → switch from Test Mode to Live Mode
  2. Settings → API Keys → Generate Live Key
  3. You get rzp_live_... keys — completely separate from test keys.
  4. Save in vault under a Live Mode environment label.

Repeat the Webhook setup (2.3) and Plan creation (2.4) inside Live Mode — they don't carry over from test mode.

Gotchas

  • Entity name must be IDENTICAL on PAN, GST, bank account, and CIN. Razorpay rejects KYC if "Azkashine Pvt Ltd" on PAN vs "Azkashine Private Limited" on GST.
  • Test keys ≠ Live keys — completely separate. Test mode accepts card 4111 1111 1111 1111 + any CVV / future expiry; real cards fail in test mode.
  • Webhook secret is a string YOU choose, not Razorpay-generated. Pick something long and random.
  • Webhook URL must be HTTPS in production. For local dev, BE team uses ngrok to tunnel localhost:5000 to a public HTTPS URL.
  • MCC 7361 (Employment Agencies) is medium-risk — expect possibly higher MDR (2.0–2.5% for cards) + small rolling reserve. Negotiable later.
  • Refund policy MUST be on the site before KYC. Even a one-liner like "₹50 lifetime is non-refundable. ₹250/month is refundable within 7 days, pro-rata." is fine.
  • For ₹250/month auto-debit: UPI Autopay has the highest success rate in India (95%+). Card e-mandate is fallback. RBI's 2026 e-mandate framework lets recurring debits ≤₹15,000 skip AFA after the first authorization.

3. DLT Registration (for SMS via MSG91)

Time: 1 hour clickwork · Approval: 1–3 weeks worst case · Output: Entity ID + Header ID + Template IDs

DLT is a government-mandated SMS permit. Without it, Indian telcos silently block your OTP SMS. Start this on Day 1 — the clock is the longest of any task in this guide.

What is DLT? DLT = Distributed Ledger Technology. India's telecom regulator (TRAI) built a blockchain-backed registration system in 2020 to fight SMS spam. Every business sending commercial SMS must register itself, its sender name, and every template body. Telcos (Jio/Airtel/Vi) block any SMS that isn't pre-registered.

3.1 Pick a DLT operator

Why: There are 5 government-authorized DLT portals. You only register on ONE — the blockchain shares your data with all other telcos automatically.
OperatorDirect linkOne-time fee
Jio Trueconnect ⭐trueconnect.jio.com~₹5,900 + GST
Airtel SmartPingsmartping.airtel.in~₹5,900 + GST
Vi Vilpowervilpower.in~₹5,000 + GST
BSNLucc-bsnl.co.in~₹4,000 + GST
Tata Teleservicestrai.tatacommunications.com~₹5,000 + GST

Recommendation: Jio Trueconnect or Airtel SmartPing — biggest install base, smoothest UX, fewest rejections. Walkthrough below uses Jio Trueconnect.

3.2 Create the Azkashine entity on DLT

Why: The "Principal Entity" registration tells TRAI "Azkashine is a legitimate business sending SMS." It's the parent record under which sender IDs and templates get registered.
  1. Go to https://trueconnect.jio.com/
  2. Click Sign up as Principal Entity (PE = business sending SMS; "Telemarketer" is for agencies, not you).
  3. Entity Type: Pvt Ltd / LLP / Partnership / Proprietorship / Trust / NGO / Government.
  4. Fill in:
    • Legal Entity Name (must EXACTLY match PAN — this trips up 80% of applicants)
    • CIN / LLPIN / Firm Registration No.
    • Address (must match GST registered address)
    • Authorized Signatory: name, PAN, Aadhaar, mobile, email (becomes the DLT account owner — pick a founder/director)
    • Business Category (pick "Computer Software" or "E-Commerce" or "Recruitment Services" — closest fit)
  5. Upload documents (PDF/JPG, each <2MB):
    EntityRequired Documents
    Pvt LtdPAN of company, Certificate of Incorporation, MOA/AOA, CIN, GST cert (if registered), Authorized signatory's PAN + Aadhaar, Authorization letter on company letterhead (template provided by operator)
    LLPPAN of LLP, LLP Agreement, LLPIN, GST cert, Designated partner's PAN + Aadhaar, Authorization letter
    ProprietorshipPAN of proprietor, Shop & Establishment OR Udyam OR GST cert (any 1), Aadhaar (Authorization not needed — proprietor IS the business)
    PartnershipFirm PAN, Partnership Deed, Partner PANs + Aadhaars, Authorization letter signed by all partners
    Trust / NGOTrust Deed / Registration Cert, 12A + 80G certs (if applicable), PAN, Trustee Aadhaars
  6. Pay entity registration fee (~₹5,900 + GST via UPI/card).
  7. Submit.

You get an Entity ID like 1701234567890123456 (18–19 digit number — a blockchain hash).

Timeline: 1–3 working days when docs are clean. 2–3 weeks if any name mismatch.

3.3 Register your Sender Header

Why: The "header" is the 6-letter brand name shown on the recipient's phone instead of a random number. Telcos require pre-approval so spammers can't impersonate banks/brands.

For Azkashine, suggest AZKSHN or AZKSJB (exactly 6 alphabetic characters, no digits, no special chars).

  1. Inside Jio Trueconnect → Headers → + Add Header
  2. Choose Category:
    • Transactional — OTP, payment confirmations, password reset (bypasses DND — what you need)
    • Service Implicit — transactional messages with implicit consent (e.g. "application accepted")
    • Service Explicit — promotional with opt-in
    • Promotional — pure marketing (10-digit numeric header, subject to DND)
  3. Enter the header: AZKSHN
  4. If the header doesn't exactly match the company name, attach a correlation document:
    • Domain WHOIS showing azkashine.com is owned by the entity
    • Website screenshot
    • Trademark certificate (if you have one)
  5. Submit → telco approval queue.

Timeline: 1–2 working days. You get a Header ID — save it.

3.4 Register your message templates

Why: Telcos require every EXACT message body to be pre-approved so spammers can't send phishing through registered senders. Each variable slot ({#var#}) is filled at send-time but the surrounding text must match the approved template.
  1. Trueconnect → Templates → + Add Template
  2. For each template fill in:
    • Template Name (internal label, e.g. "OTP_LOGIN")
    • Template Type: Transactional / Service Implicit / Service Explicit / Promotional
    • Header: pick AZKSHN
    • Template Content: paste the EXACT body, using {#var#} for variables

Templates to submit for Azkashine v1

Template 1: OTP_SIGNUP_LOGIN (Transactional)
Body: Your Azkashine verification OTP is {#var#}. Valid for 10 mins. Do not share with anyone. -AZKSHN

Template 2: PAYMENT_CONFIRMED (Service Implicit)
Body: Payment of Rs {#var#} received for your Azkashine subscription. Active till {#var#}. Thank you. -AZKSHN

Template 3: PASSWORD_RESET_OTP (Transactional)
Body: Your Azkashine password reset OTP is {#var#}. Valid for 10 mins. Do not share. -AZKSHN
  1. Submit each. Telco reviews body for:
    • Spam / fraud language
    • Unregistered URLs (URLs must be pre-whitelisted separately — easiest: omit them)
    • Variable syntax: must be {#var#}, NOT {{var}}, NOT [var]
  2. After approval, each template gets a Template ID (long hash).

Timeline: 1–3 working days per template.

3.5 Map approved templates into MSG91

After you get the DLT Template IDs from Trueconnect, you map them into MSG91 (covered in Section 4 → 4.4).

3.6 Save in vault for audit

Why: You don't directly hand the DLT IDs to the BE team — they get pasted into MSG91 and BE uses MSG91's internal template ID. But the vault keeps a record for annual renewal audits.
DLT Operator: Jio Trueconnect
Entity Name: <legal name>
Entity ID: 1701234567890123456
Header: AZKSHN (Transactional)
Header ID: <id>
Templates:
  - OTP_SIGNUP_LOGIN — DLT Template ID: <id>
  - PAYMENT_CONFIRMED — DLT Template ID: <id>
  - PASSWORD_RESET_OTP — DLT Template ID: <id>
Signatory: <name>, <PAN>
Renewal: typically annual (~₹1,500/yr renewal fee)

Gotchas

  • Legal entity name on PAN vs GST vs CIN vs DLT — all must be IDENTICAL. Spelling, abbreviation, "Pvt Ltd" vs "Private Limited" — any difference = rejection.
  • Variable syntax MUST be {#var#}. #1 template rejection reason.
  • Don't put URLs in OTP messages. Each URL needs a separate URL whitelist registration.
  • OTP = Transactional category, NOT Service. Wrong category = DND-blocked = OTPs fail for users on DND list.
  • End SMS with the header in dashes, e.g. -AZKSHN. Reduces rejection chance.
  • Don't pick fancy 6-char headers — AZKJOB, BUYNOW, WINBIG get rejected. Stick to brand-name-based.
  • Annual renewal — DLT entity registration renews annually (~₹1,500/yr). Calendar reminder for 11 months out.
  • TRAI fines — sending SMS without DLT = ₹5,000 per violation. Don't try to hack around it.

4. MSG91 (SMS + WhatsApp + Email — all in one account)

Time: 5 min signup · WhatsApp prereq: Meta verification 1–2 weeks · One Auth Key for all 3 channels

MSG91 is the actual sender — they push SMS to telcos, push WhatsApp via Meta, push email via SMTP. One account handles all three channels with one Auth Key.

4.1 Create the MSG91 account

Why: MSG91 is the courier. DLT and Meta give permission; MSG91 actually delivers. We need their account before any of the channels can work.
  1. Go to https://msg91.com → top right Sign Up
    Direct signup: https://control.msg91.com/signup/
  2. Sign up with @azkashine.com email.
  3. Fill in:
    • Name: Azkashine
    • Business email
    • Mobile number (gets OTP)

Record 1 (SPF)
Type: TXT

Type: TXT

Value: <long crypto key MSG91 gives you>

Record 3 (DMARC) — optional but recommended
Type: TXT
Host: _dmarc
Value: v=DMARC1; p=quarantine; rua=mailto:dmarc-reports@azkashine.com

5. Multi-Language Strategy & Cost

Languages in scope: 10 Indian languages (English, Hindi, Tamil, Telugu, Kannada, Malayalam, Bengali, Marathi, Gujarati, Punjabi) · Per project charter

Job seekers come from different states and we support 9–10 languages in the UI. But sending notifications in those same languages affects each channel differently — some are free, one is expensive.

5.1 Channel-by-channel summary

Channel Languages supported Cost impact per language Template approval burden
SMS Unlimited (Unicode), each language = NEW DLT template to register 1.5–2× more per send for non-English 3 base × 10 lang = 30 DLT templates
WhatsApp 60+ languages, each = NEW Meta-approved template Same cost as English 12 base × 10 lang = 120 Meta templates
Email Unlimited (Unicode/UTF-8) Same cost as English 4 base × 10 lang = 40 templates (no external approval)
Takeaway: WhatsApp + Email are language-neutral on cost. SMS is where multi-language gets expensive.

5.2 SMS — the expensive one

Why SMS gets expensive in regional languages: English uses GSM-7 encoding (160 chars/segment). Indian scripts (Hindi/Tamil/Telugu/Bengali/Marathi/Gujarati/Kannada/Malayalam/Punjabi) all use Unicode UCS-2 encoding (only 70 chars/segment). So the same OTP message becomes 2–3 segments in regional languages, and you pay per segment.

Cost example — typical OTP message

"Your Azkashine verification OTP is 123456. Valid for 10 mins. Do not share. -AZKSHN" = ~85 characters

LanguageEncodingChars/segmentSegmentsRate/segmentCost/SMS
EnglishGSM-71601~₹0.20~₹0.20
Hindi (Devanagari)Unicode702~₹0.20~₹0.40
TamilUnicode702~₹0.20~₹0.40
Telugu / Bengali / Marathi / Gujarati / Kannada / Malayalam / PunjabiUnicode702–3~₹0.20~₹0.40–0.60

The same OTP costs 2× in any regional language vs English. Longer messages (interview reminders, payment confirmations) can hit 3× because they spill to a 3rd segment.

DLT registration burden

  • Every language needs a SEPARATE DLT-approved template
  • 3 base templates (OTP, payment confirm, password reset) × 10 languages = 30 DLT templates to register
  • Each template approval = 1–3 working days
  • Direct cost: ₹0 per template (DLT entity fee already paid). Operational time: 2–4 weeks to file all 30.

5.3 WhatsApp — cost-neutral, best channel for multi-language

Why WhatsApp is the smart channel for an Indian regional-language portal: Cost per message is identical regardless of language. Native scripts render correctly. The 24-hour customer service window makes Utility messages FREE. That's why the project charter locks WhatsApp as the primary channel and SMS as fallback.

Coverage

  • WhatsApp Business API supports 60+ languages — way more than your 10
  • Each language version is submitted separately to Meta for approval
  • 12 templates × 10 languages = 120 template approvals (minutes to 24h each, can submit in batches)

Cost — same regardless of language

Template typeCost in any language
Authentication (OTP, password reset)~₹0.115/msg
Utility (job status, interview reminders, payment confirmation)FREE inside 24h customer-service window, else ~₹0.115/msg
Marketing~₹0.78/msg (avoid)

5.4 Email — also cost-neutral

  • UTF-8 handles all 10 Indian scripts natively — no encoding penalty
  • Same cost per email regardless of language: ~₹0.10–0.15/email
  • Templates: 4 base × 10 languages = 40 email templates in MSG91 dashboard (no external approval needed)
  • Operational lift: low — translate once, paste into MSG91, done

5.5 Phased rollout recommendation

Why phase the rollout: Filing 30 DLT templates + 120 Meta templates simultaneously is a procurement bottleneck. Starting with 2 languages covers most of your user base in v1 and lets the rest land over the following weeks without blocking launch.

Phase 1 — Launch (Sprint 1-3)

  • English + Hindi only on all channels
  • Covers ~70% of users + diaspora
  • 6 SMS DLT templates (3 × 2 languages)
  • 24 WhatsApp templates (12 × 2 languages)
  • 8 email templates (4 × 2 languages)
  • ~80% less procurement load than 10-language launch

Phase 2 — Post-launch (over 4–6 weeks)

  • Add Tamil, Telugu, Kannada, Malayalam, Bengali, Marathi, Gujarati, Punjabi
  • Roll out per-region as user base grows
  • Spread the DLT/Meta approval load across multiple weeks
  • Each new language unlocks per state's user adoption

5.6 Monthly cost cheat-sheet

Realistic estimate at ~10,000 active users (assumption: 2 OTPs + 3 Utility notifications per user per month):

ScenarioSMSWhatsAppEmailTotal / month
English-only~₹4,000~₹2,300~₹500~₹6,800
English + Hindi (Phase 1)~₹5,400~₹2,300~₹500~₹8,200
All 10 languages (Phase 2)~₹6,800~₹2,300~₹500~₹9,600

Multi-language premium = roughly +₹2,800/month at 10K users, almost entirely from SMS Unicode penalty. WhatsApp + Email are essentially free to scale across languages.

Scaling to 100K users

  • All 10 languages, 100K users → estimated ~₹80,000–100,000/month total notification spend
  • Vast majority of that is SMS — strong financial case to push WhatsApp adoption (use SMS as fallback only)

5.7 Important note to flag for senior

The 10-language launch promise from the project charter §4.1 is mostly about UI strings — buttons, labels, error messages — which is a one-time translation cost already in scope.

Notification templates are a SEPARATE deliverable that needs explicit ownership:

  • DLT template registration: ~30 templates × 1–3 days approval each
  • WhatsApp template approval: ~120 submissions to Meta
  • Translation cost: budget for native-speaker review on every message body (a wrong word in a Tamil OTP gets reported as a scam — high reputational risk)
  • Recommended: launch with English + Hindi for v1, file the other 8 languages post-launch as user adoption grows in each region
